## 3. 合入的社区能力

### 3.1 DFlash-family 正确性与模型能力

- anchor sampling 不再受 batch padding 干扰；
- 要求相邻监督 token，并支持 partial tail；
- loss 使用可累加分子/分母，在 DP rank 间聚合后再相除；
- 修复 eager attention mask；
- 支持 sliding-window 和 full/sliding 混合 attention layer；
- DFlash/Domino 支持 FlexAttention FLASH backend；
- 增加 constant/cosine 学习率调度。

这些变化会改变部分训练样本组成和 loss 基线，是有意的上游语义变化，没有在本地
回退。

### 3.2 DSpark 与 capture server

- DSpark capture method 从复用 `dflash` 改为独立的 `dspark`；
- SGLang v0.5.14 patch 增加异步 capture streaming；
- capture request 改为 `max_new_tokens=0` 的纯 prefill；
- 增加 Kimi-K3 DSpark capture、配置和独立 patch；
- 增加 Inkling managed capture 和多节点示例。

### 3.3 Ascend、ROCm、Mooncake 与分布式运行

- Ascend managed-local 分布式在线 DFlash 训练配置；
- Ascend capture segment 的独立 CPU mount overlay；
- AMD ROCm 安装、训练 recipe、结果图和已知问题；
- Mooncake lease、pinning、durable sample 回收和 shutdown 清理；
- 无共享 rank inbox 时的 HTTP inbox relay；
- 跨节点 checkpoint 同步工具。

### 3.4 数据、缓存、追踪和 CI

- 修复 CodeAlpaca `input` 字段和 native tool list 解析；
- prompt cache 纳入 chat-template 指纹；
- prompt shuffle 支持独立 `prompt_seed`；
- W&B 记录 resolved config 并递归脱敏；
- CI 清理残留 GPU 进程，同时保护 `nvidia-persistenced`。

## 4. 合并时保留的本地能力

### 4.1 DSpark 词表裁剪

本地适配允许 draft config 使用小于 target vocabulary 的 `draft_vocab_size`，核心
能力包括：

- 统一的 `DraftVocabMappingMixin`；
- `t2d`、`d2t` 注册、安装、形状和内容一致性校验；
- target label 到 draft id 的转换和裁剪外 ignore label；
- `markov_w1` 保持 target 全词表，`markov_w2` 使用 draft vocabulary；
- objective、CE 分母和 acceptance 对裁剪词表的正确处理；
- mapping 版本变化时使裁剪 head 缓存失效；
- full-vocab 路径保持旧 checkpoint、公式和 collective 行为；
- checkpoint resume 时拒绝内容不一致的新 mapping。

### 4.2 数据与 mapping 工具

- `scripts/build_vocab_mapping.py`；
- `scripts/filter_trainable_conversations.py`；
- 从 JSONL 或离线 feature 统计有效 token；
- token count 缓存及 corpus identity 校验；
- `--minimum-valid-tokens` 和 DSpark 相邻监督 token 过滤；
- 无需重抓 hidden states 即可生成或审计 mapping。

### 4.3 梯度尖峰保护

- `off`、`observe`、`on` 三种模式；
- 非有限梯度和相对异常梯度诊断；
- 可跳过异常 optimizer step；
- 连续跳步熔断、重新基线及 checkpoint 状态恢复；
- 与上游 controller 性能指标并存。

## 6. 合并后的专项修复

### 6.1 离线 DSpark hook 兼容

上游把 DSpark method 改为 `dspark`，但 stock SGLang v0.5.14 Qwen3 只有
`set_dflash_layers_to_capture`。原组合会在离线 target model 构建阶段直接失败。

现在的选择顺序是：

1. 优先使用 `set_dspark_layers_to_capture`；
2. 缺失时 warning 并回退 `set_dflash_layers_to_capture`；
3. 两者都不存在才报错。

该回退只作用于 DSpark，不改变 Eagle3/DFlash hook 行为。

### 6.2 SGLang patch 截断与部署兼容

Ascend mount 逻辑加入后，`spec_capture_sink.py` 新文件 hunk 实际为 431 行，但
header 仍声明 395 行。`patch` 应用后会截断尾部，丢失 `put_sample()`、`_SINK`、
`maybe_init_sink()` 和 `get_sink()`，server 初始化时会 `AttributeError`。

已完成：

- hunk header 修为 431；
- index 更新为真实 blob 摘要；
- 抽取 sink 新文件 hunk，在空目录真实执行 `patch -p2 --batch`；
- 新增全仓 `.patch` hunk 声明/实际行数静态测试；
- 断言生成文件末尾存在 `get_sink()`。

部署端必须同步升级 patch。当前 SpecForge 会发送 `dspark` 和纯 prefill 请求，旧
patch 不支持这一协议组合。升级操作和兼容矩阵见：

- `my_docs/2026-08-12_0812_upstream_组合风险核实与修复.md`

### 6.3 Ascend Mooncake 与配置

- 原本没有 apply 入口的独立 Ascend mount overlay 已删除；
- CPU segment mount 合入 v0.5.14 主 patch；
- Ascend 下 `local_buffer_size=0`，非零配置会明确 warning；
- `global_segment_size_bytes` 仍是实际 server 容量，不会被清零；
- NPU recipe 将不确定的 `default_kv_lease_ttl_ms` 显式设为 `null`，待目标
  `mooncake_master --help` 确认支持后再启用。

### 6.4 历史 feature 资格扫描

新增 `scripts/scan_offline_feature_eligibility.py`，按训练 `max_length` 复现
“截断后必须有两个相邻监督 token”的规则，并区分：

- 截断后仍兼容；
- 由截断导致无效；
- 原始完整样本就无效；
- 文件损坏或无法读取。

不可读文件不会再让 `ProcessPoolExecutor` 整轮退出；它们单独计入
`unreadable_files`，同时写入 `--invalid-paths-output`。CLI 有进度输出，存在无效
或不可读文件时返回非零退出码。

### 6.5 `.ckpt.gz` 早停读取

原扫描器对每个 gzip feature 全量解压，而生产样本的大部分内容是 hidden states。
新增的 `read_feature_keys_streaming()` 顺序解析 PyTorch ZIP local header 和 data
descriptor，只读取指定 tensor 的 storage：

- scan 只取 `loss_mask`；
- 训练词频统计取 `input_ids` 和 `loss_mask`；
- 两者都位于大 hidden-state storage 前，可以提前停止解压；
- `.ckpt` 仍走原 `torch.load(..., mmap=True)`；
- 旧序列化、非 STORED member、异常顺序、签名或 metadata 不符合预期时回退原
  `load_feature_file()`，只允许变慢，不允许改变结果。

回退 warning 在每个进程中按异常类型只报一次；扫描主进程最终按原因汇总文件数，
避免 60 万文件逐条刷屏。

### 6.6 bounded smoke 与正式 mapping

`--filter-candidate-samples` 可以在 deterministic shuffle 后、tokenize 前限制候选
数量，适合 600k 语料 smoke。但候选集不完整时现场生成裁剪 mapping 会得到不稳定
的 `t2d/d2t`。

最终规则：

- full-vocab 运行允许 bounded candidate；
- 裁剪词表且现场生成 mapping 时继续拒绝 bounded candidate；
- 裁剪词表可以通过 `--vocab-mapping-path` 复用正式 mapping；
- 复用前校验 `d2t.shape == (draft_vocab_size,)`；
- 复用前校验 `t2d.shape == (target_vocab_size,)`。

## 7. 用户后续提交的修复（`a510465`）

### 7.1 训练启动阶段词频统计也改成流式读取

前一轮只优化了扫描脚本，但训练在没有显式 `model.vocab_mapping_path` 时会调用
`_ensure_offline_vocab_mapping()`，每个 rank 都通过
`count_effective_feature_tokens()` 遍历所有 feature。旧实现仍使用
`load_feature_file()`，对 `.ckpt.gz` 全量解压 hidden states，训练会长时间停在第一
步之前。

用户在 `a510465` 中将该路径改为复用 `read_feature_keys_streaming()`，只取
`input_ids/loss_mask`。对于 500 个及以上文件，每约 5% 输出一次 heartbeat。这里
没有使用进程池，因为它运行在 accelerator/distributed 初始化之后，fork worker
不安全；早停读取本身已经去除了主要开销。

### 7.2 复用 mapping 必须随 feature 目录发布

此前 `--vocab-mapping-path` 只验证并返回外部文件路径，`output_path` 下没有留下
mapping。后续训练若没有再显式设置 `model.vocab_mapping_path`，会从 bounded smoke
feature 重新派生 mapping，重新引入本应禁止的不稳定映射。

`a510465` 将验证通过的源文件按字节复制到：

```text
<output-path>/vocab_mapping/vocab_mapping.pt
```

实现使用同目录临时文件和 `os.replace()` 原子发布；若源文件已经是目标文件则 no-op，
避免 self-copy。复制原始字节而不是重新序列化，也保留未来 mapping 格式可能增加的
额外字段。这样“生成 mapping”和“复用 mapping”对 feature 目录提供相同契约。

## 8. 行为变化与兼容性结论

| 场景 | 结论 |
| --- | --- |
| 本地 DSpark 裁剪 objective/CE/acceptance | CPU 单测范围内保留，没有被上游覆盖 |
| full-vocab DSpark | CPU/桩测试确认保留旧 checkpoint、公式和 collective 代码路径；未做设备端训练验收 |
| 旧 checkpoint + 新 mapping | 拒绝；resume 必须复用原 mapping |
| 当前 SpecForge + 旧 v0.5.14 patch | 不兼容，必须升级 capture server patch |
| stock Qwen3 离线 DSpark | 静态代码和 mock hook 测试确认 DFlash fallback；未用真实 SGLang 模型端到端执行 |
| 坏 `.ckpt.gz` 扫描 | 记录 unreadable，继续扫描其他文件，整体非零退出 |
| 不支持流式格式的合法 feature | CPU 单测确认自动回退全量读取且测试样本结果一致 |
| bounded candidate + 现场生成裁剪 mapping | 继续禁止 |
| bounded candidate + 已验证正式 mapping | 支持，并把 mapping 发布到 feature 目录 |
| 相邻监督 token 规则 | 保留上游语义；旧数据需扫描或重抓，不默认静默 skip |

未发现已测范围内的功能失效。以下能力仍属于未验证边界，而不是“已确认无风险”：

- Ascend NPU 上真实模型 forward/backward、HCCL/EP 和 checkpoint resume；
- 已部署 SGLang 树真实 reverse/apply 和 capture server smoke；
- Mooncake 多节点、lease TTL 和 CPU segment 容量压力；
- CUDA/Blackwell FlexAttention；
- AMD ROCm；
- 60 万生产 feature 的完整扫描耗时和实际 unreadable 数量。
