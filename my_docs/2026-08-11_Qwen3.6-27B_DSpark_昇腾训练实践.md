# Qwen3.6-27B 投机解码：昇腾（Ascend）上的 DSpark 草稿模型训练实践与小词表适配

> **摘要**：本文记录在昇腾 NPU 上为 Qwen3.6-27B 训练 DSpark 投机解码草稿模型的完整实践。与业界既有实践（在线特征 + 全词表）不同，本工作走的是**离线特征 + 词表裁剪**路线：为上游 SpecForge 的 DSpark 补上此前被架构契约明确禁止的词表裁剪能力（248320 → 64000 / 32000），并定位修复十余项在真实数据规模下才暴露的正确性与可用性问题——其中离线特征读取的启动期回归让训练在双机 16 卡上静默卡死 46 分钟，梯度尖峰在一次 10480 步的记录跑里四次抹掉约 4000 步进展。目前已产出 4 个草稿模型（1 个全词表基线、2 个小词表、1 个领域微调），基准评测与 MTP 对比进行中，结果将持续更新至本文。

---

## 1. 背景：为什么是 27B，为什么是小词表

投机解码（Speculative Decoding）的账很好算：轻量草稿模型一次提出多个候选 token，目标模型单次前向并行验证，在不改变输出分布的前提下摊薄串行步数。模型越大，这笔账越划算。

但 753B 那个量级的收益是显然的，27B 这个量级反而更值得做——它是**私有化部署与端侧服务的主力尺寸**，卡数有限、并发不高、单请求延迟敏感，而"每 token 一次完整前向"的串行成本在这类场景里同样是主要矛盾。区别在于：753B 上草稿模型的开销相对目标模型可以忽略不计，27B 上不行。**草稿侧每一份显存、每一次访存都要算进总账**，这直接决定了本文的技术选择。

Qwen3.6-27B 的具体形状：64 层，`hidden_size=5120`，**`vocab_size=248320`**。最后这个数字是本文的起点——它比 Qwen3 系列的 151936 大了 63%，而草稿模型这一侧，词表维度上的开销是**线性甚至平方级**地跟着走的：

- Markov Head 的低秩分解 `B = W1·W2`，`W1 ∈ R^{V×r}`、`W2 ∈ R^{r×V}`，r=256 时两块加起来 **127.4M 参数**——草稿模型本体才 5 层；
- 训练目标要在 `[B, N, K, V]` 上做分布对齐，V=248320 时这个张量大到必须分块（`objective_chunk_blocks`）才能算。

**而这个词表的绝大部分在真实语料里根本用不上。** 我们在 600k 通用语料上统计：出现频率最高的 64000 个 token 覆盖了 98.9% 的可训练位置，32000 个覆盖 95.8%。剩下那 18 万多个 token 占据了 3/4 的参数量，贡献了 1.1% 的覆盖率。

### 1.1 草稿模型的技术路线

| 方案 | 一次前向的草稿产出 | 训练目标 | 说明 |
|---|---|---|---|
| MTP | 1 个 token | 简单 | 目标模型自带，是内置基线 |
| EAGLE-3 | 递归多 token（串行） | 中等 | 多步能力强，递归依赖使训练与部署适配复杂 |
| DFlash | 一个完整 block（并行） | CE 单损失 | 块级并行草稿，结构轻、吞吐友好 |
| **DSpark** | **并行 block + 块级置信度** | **CE/L1 + 置信度头** | DFlash 增强：Markov Head 建模块内依赖，Confidence Head 预测接受概率供推理端裁剪提案 |

DSpark 的关键机制是**锚点驱动的并行块生成**：在序列中采样锚点（anchor），每个锚点生成一个 token 块（本工作 block_size=16），全部块在单次前向内并行完成。

这一机制的几点独有优势：草稿生成**零递归依赖**，全部草稿在一次前向内完成，草稿侧开销低、延迟可预期；**训练信号密度高**，单条序列可采样数百个锚点（本工作 512 / 1024），每个锚点贡献一个块的并行监督信号；**Markov Head** 以低秩状态转移建模块内 token 间的条件依赖，使并行产出的块仍具语言连贯性；**Confidence Head** 输出块级接受概率，推理端可按置信度排序并提前截断低置信提案，把验证浪费转化为可调的运行时开销。

### 1.2 训练框架与路线选择

我们基于 **SpecForge**（SGLang 社区的草稿模型训练框架）开展这项工作。相比另一条生态（vLLM 社区的 speculators），SpecForge 的 DSpark 实现忠实于原论文的"共享冻结 target lm_head + 全词表"设计——**这正是缺口所在**：`AlgorithmCapabilities.supports_vocab_mapping` 对 DSpark 是 `False`，而且这条契约被测试保护着，`DSparkDraftModel` 的继承链完全不经过 `Eagle3DraftModel`，连 `t2d`/`d2t` buffer 都不存在。

而 speculators 从 DSpark 的第一版实现（#677）就带着词表裁剪，`MarkovHead` 一诞生就是 `verifier_vocab_size` / `draft_vocab_size` 双参数；已发布的 `novita/kimi-k2.6-dspark` 就是 163840→32000 的 5.1× 裁剪，跑在生产里。**所以这不是"要不要做"的问题，是"SpecForge 缺了另一条生态已有的能力"。**

特征通路上我们选了**离线路径**：先用 `prepare_hidden_states.py` 把目标模型 5 个层位的隐状态离线采集落盘，再由训练侧消费。这个选择绕开了在线 capture 那一整块昇腾适配（sglang backend、post-norm hook、ring flash-attn 的 Ascend 版本），代价是要付一次全量特征的存储和一次采集时间。对 27B + 600k 这个组合，这笔交换是划算的。

## 2. 目标与挑战

**目标**：为 Qwen3.6-27B 训练生产可用的 DSpark 草稿模型，训练全流程运行在昇腾 NPU 上，并验证词表裁剪能否在不损失接受率的前提下把草稿侧开销压下来。

挑战集中在三处：

**其一，词表体量决定了草稿侧的成本结构。** V=248320 时，Markov 头 127.4M 参数、objective 段必须分块计算。要把这块压下来，就得给 SpecForge 的 DSpark 补上一条它在架构上明确拒绝的能力，而且要保证**不开裁剪时的行为与基线逐位一致**——这是整个改动能被接受的前提。

**其二，上游框架在真实数据规模下暴露的正确性与可用性问题。** 27B × 600k × 离线路径这条组合没有现成路径，打通过程中定位的问题包括：离线 reader 在组装期探查每个特征文件，gzip 下等于启动前把整个数据集串行解压一遍（**双机 16 卡实测静默卡死 46 分钟，零日志**）；离线路径没有退化样本过滤，导致 DSpark 的 anchor 硬校验直接报错；词表映射构建是 O(V×K) 的 Python 线性扫描（V=248320/K=64000 时昇腾上几分钟，且发生在无日志阶段）；token 统计整列物化导致 OOM；`Dataset.from_generator` 未钉 `cache_dir` 把 home 分区写满。这些在小模型小数据集上都不显形。

**其三，长跑稳定性。** 600k 级数据 × 多 epoch 对应数万步，而一次记录在案的 27B 跑在 10480 步里**四次**把 accuracy 从 0.55 砸到 0.15，每次损失约 4000 步进展——`max_grad_norm` 一次都没挡住，而且机理上挡不住。

### 本文工作与结果一览

1. **能力补齐**——为 SpecForge 的 DSpark 实现词表裁剪（t2d/d2t），一行配置开关，248320 → 64000 / 32000，objective 段显存 2.18×，Markov 头参数 127.4M → 80.0M / 71.8M；
2. **管线打通**——27B × DSpark × 昇腾 × 离线特征的完整训练管线，涵盖数据可训性过滤、启动期回归修复、映射构建链路与评测侧对齐；
3. **长跑稳定性**——梯度尖峰控制限，对记录轨迹 4/4 命中、858 个健康步 0 误伤；
4. **模型产出**——4 个草稿模型（全词表基线 / 32k / 64k / 领域微调），评测进行中。

## 3. 系统架构与训练管线全景

### 3.1 离线两段式架构

采用"采集 + 训练"两段分离：

**采集侧（昇腾 NPU）**：`prepare_hidden_states.py` 加载 Qwen3.6-27B，按 `target_layer_ids=[2, 17, 32, 47, 62]` 抽取 5 个层位的隐状态，连同 `input_ids` / `loss_mask` / `target_last_hidden_states` 一起落盘为特征文件。

**训练侧（昇腾 NPU）**：`specforge train --config <yaml>` 消费特征目录，草稿模型（5 层、`hidden_size=5120`、`block_size=16`、`markov_rank=256`）在块内因果注意力约束下一次前向并行预测整个 token 块。

这条路径最省事的地方在于：DSpark 的离线特征只有 `input_ids` / `loss_mask` / `hidden_states` / `target_last_hidden_states`，**全部与词表无关**。这意味着**调整 `draft_vocab_size` 不需要重跑采集**——同一份特征可以喂给 K=32000、K=64000 和全词表三种训练。这个性质是词表裁剪能低成本迭代的前提，也是我们把映射构建单独做成一个工具的原因（§4.5）。

一个必须写进操作手册的坑：**采集时不要加 `--compress`**。原因见 §4.2。

### 3.2 适配全景

| 方向 | 核心问题 | 解决思路 |
|---|---|---|
| **模型能力** | DSpark 无词表裁剪，且 `supports_vocab_mapping=False` 是被测试保护的架构契约 | 新增 `DraftVocabMappingMixin` 统一 t2d/d2t 生命周期；Markov 头 W1/W2 词表分离；混合目标的硬标签经 t2d 映射（§4.1） |
| **数值正确性** | 裁剪后教师分布在 K 维重归一化，`accept_probability` 系统性偏高——**未裁剪时这个量本来就是精确 speculative decoding 的接受率**，裁剪静默改变了它的语义 | 蒸馏损失与接受概率用两个不同的教师；全词表归一化因子分块 logsumexp，`[..., V]` 张量始终不物化（§4.1） |
| **回归防护** | "未裁剪路径不变"这个上线前提，基于单元测试的结论**三次都不成立** | 双 worktree 差分验证：loss / accuracy / 全部 ratio metrics / 全部梯度做 sha256 逐位比对（§4.1） |
| **启动吞吐** | 离线 reader 组装期探查每个特征文件，gz 必须整份解压；每 rank 各付一遍 | 组装期只 `os.walk` 列文件名，完整校验降级为环境变量 opt-in（§4.2） |
| **数据可训性** | DSpark 要求 anchor 位置 i 与 i+1 都是 loss token，离线路径无过滤 | 在源 JSONL 上按真实预处理语义过滤；采集侧补 `--minimum-valid-tokens`（§4.3） |
| **长跑稳定性** | 梯度尖峰四次抹掉约 4000 步；`max_grad_norm` 界范数不界方向 | 运行几何均值的无量纲倍数作控制限，超限整步丢弃，Adam 矩不动（§4.4） |
| **映射构建** | 建图 O(V×K) 线性扫描；换一个 K 就要重扫整个数据集 | scatter 构建；计数与选 K 按代价切开、计数结果带指纹缓存（§4.5） |
| **评测通路** | DeepSpec 完全没有裁剪概念，`verify_draft_tokens` 用 target 空间 id 去 gather | K 维归一化后散射回 V 维；四处对齐（§4.6） |

训练配置：5 层草稿解码器、`block_size=16`、目标层位 `[2,17,32,47,62]`、`markov_rank=256`、lr 6e-4 cosine、损失 `{ce: 0.1, l1: 0.9}` + 置信度头、`loss_decay_gamma=4.0`。

## 4. 关键问题与解决方案

### 4.1 主线：给 DSpark 补上词表裁剪

对着 speculators 读了一遍，有两点是自己不一定能想到的。

**其一，W1 和 W2 不共享词表。** `W1` 由**上一个真实 token** 索引，那个 token 可能是任意 target id，所以必须保持全词表；`W2` 输出的偏置要叠到 draft logits 上，所以跟随裁剪。SpecForge 原本两边都用 `self.vocab_size`。这是设计上真正"想清楚了"的一点。

**其二，词表裁剪不会让草稿模型"学得更难"，反而更容易。** 因为教师和学生被施加了完全相同的限制——`lm_head` 和 `verifier_lm_head` 是同一份 target lm_head 按同一个 `t2d` 切出来的行，损失在 K 维上 softmax，意味着教师分布也被限制并重归一化了。学生要拟合的是 `p|_K`，比全词表目标更简单，去掉的是长尾上那部分几乎学不出来也几乎采不到的质量。

真正的代价只有一个，而且是硬上界：**任何落在 draft 词表外的 target token，草稿永远提不出来，那个位置必然被拒。接受率天花板 ≈ 训练分布下 top-K 的覆盖率。** 这也是为什么 `draft_vocab_coverage` 必须做成训练指标出现在日志里，而不是事后审计。

#### 混合目标带来的额外一道工序

speculators 是纯软分布蒸馏（KL/TV/CE 都在 K 维 softmax 上），SpecForge 的 DSpark 是**混合目标**：硬标签 CE（α=0.1）+ 软分布 L1（α=0.9）+ confidence BCE。

硬标签这条 speculators 没有，所以裁剪时多一道工序：`target_ids` 是 target 词表的真实 token id，必须经 `t2d` 映射到 draft 空间，落在词表外的要排除。**这一步不能省，否则会出现"标签 id 越界 / 指向错误行"的静默 bug。** 而且 CE 拿到了自己的分母：被裁的标签同时退出分子和分母，否则 `alpha_ce` 会随覆盖率漂移。

#### 接受概率：一个必须拆成两个的教师

裁剪后教师分布在 K 维重新归一化，原来的 `accept_probability = 1 - 0.5·L1(q, p̃)` 会**系统性偏高**——真实接受率是 `Σ_K min(q_i, p_i)`，用的是**未归一化**的 `p_i`，而 `p̃_i = p_i/Σ_K p ≥ p_i`。反例：target 在 4 个 token 上均匀、K 只保留 2 个、草稿恰好等于条件分布，当前代码算出 1.0，真值 0.5。

关键在于**未裁剪时这个量本来就是精确 speculative decoding 的接受率**，所以裁剪静默改变了它的语义，是回归而不只是不精确。修法是把两个教师分开，合并任何一边都是错的：

| 用途 | 教师 | 理由 |
|---|---|---|
| L1 蒸馏损失（α=0.9） | `p̃`，在 K 上重归一化 | 草稿物理上无法在 K 外放质量，其分布在 K 上必然和为 1。目标若改用和为 `m<1` 的真实 `p`，损失会有 `1−m` 的不可约下界并整体压偏梯度 |
| `accept_probability` | 真实 `p`，和为 `m ≤ 1` | 它是对服务端接受率的**预测**（喂 confidence head 的 BCE 目标和 `tau_probabilistic`）。被裁掉的概率质量在服务时是真实的拒绝 |

全词表归一化因子用 `_full_vocab_logsumexp()` 分块求：按词表走 `lm_head.weight`，每块立即 `logsumexp` 归约成标量，再用可结合性合并。**裁剪要避免的 `[..., V]` 张量始终没被物化**，调用点在 `no_grad` 内，不产生激活显存和反传。顺带新增指标 `teacher_kept_mass`，它界的是**单步**接受概率。

#### 三个工程决定

**惰性切头 + 版本号缓存。** 训练模型在 `build_model_bundle` 里就构造好了，但 t2d/d2t 要到 `_ensure_offline_vocab_mapping` 才装上。所以裁剪头必须首次使用时才切，并按草稿模型的 `vocab_mapping_version` 做缓存键，后装的映射才能生效。

**`vocab_mapping_loaded` 做成从 buffer 派生的 property，而不是安装时置位的标志。** buffer 也会经由 `load_state_dict` / `from_pretrained` 进来，而那两条路径不调用我们的任何方法。做成标志位的话，一个正确保存的裁剪 checkpoint 重新加载后会报告"没装映射"然后拒绝运行。改成 `bool(t2d.any())` 就一劳永逸——全零的初始 buffer 正是"还没装"的无歧义状态。

**不裁剪时不注册 buffer。** 无条件注册会给所有存量全词表 checkpoint 的 state dict 加上两个键，而 warm start 把任何缺失键都当致命错误。藏在 `use_draft_vocab` 后面，存量 checkpoint 逐字节可加载。

#### 收益：实测显存与推算参数量

实测（CPU fp32，V=151936、K=32000、block=7、chunk=128 blocks=896 token）：

| 配置 | objective 段分配 | 相对 |
|---|---|---|
| 全词表 | 5.874 GiB | 1.00× |
| 裁剪 K=32000 | **2.690 GiB** | **2.18×** |
| 裁剪 K=32000（若不做接受率修正） | 2.477 GiB | 2.37× |

H=256 与 H=1024 两次测得比值都是 2.18×，说明该段由词表维张量主导、比值不随 hidden size 变化。

几点必须说清楚，**因为早期分析里我们自己写错过**：

- 早期文档给出的 4.75× 是**错的量纲**——那是 `[B,N,K,V]` 单个 logits 张量的比值，不是 objective 段的整体比值。confidence head、markov 的 rank 维中间量、hidden 相关张量都不随词表缩小。
- 接受率修正的显存代价只有 +0.21 GiB（+8.6%），比预估小得多，因为分块后立即归约。
- **新增固定开销**：裁剪头拷贝 ≈ `K × H × dtype_bytes`。27B（H=5120）推算 K=64000 时 bf16 约 655 MB、K=32000 约 327 MB，且修正之后 `self.lm_head` 全量权重不能释放。
- **参数侧是干净收益**：Markov 头 127.4M → 80.0M（K=64000）/ 71.8M（K=32000），只有 W2 缩小。推算，未实测。

#### "未裁剪路径不变"，被证伪了三次

上线前提是：不开小词表时，行为与基线 `7712377` 完全一致。我们一开始基于单元测试就下了这个结论，**事实证明三次都不成立**。

差分验证的方法是：同一脚本在两个 worktree（HEAD / 基线）各跑一次，对 loss、accuracy、全部 ratio metrics 的分子分母、以及全部梯度做 sha256 逐位比对，覆盖 4 种配置（默认 / `loss_decay_gamma=3` / alpha 重排 / `ce_alpha=0`）。三处偏差，**没有一处是单元测试能发现的**：

1. **resume contract 多了一个 key——已在真实集群上炸过。** 无条件写入 `dspark_draft_vocab_size` 会让本功能之前产出的**所有** DSpark checkpoint 全部无法 resume。真实报错：`ValueError: checkpoint ...-step10000 does not record required algorithm resume semantic dspark_draft_vocab_size`。而该字段在未裁剪时只可能等于 `vocab_size`。改为仅在 `use_draft_vocab` 时写入。
2. **`loss_decay_gamma` 非空时最终 loss 不逐位相同。** 把 loss 拆成两个分母分别相除后，`x/D + y/D` 与 `(x+y)/D` 在 D 为非整数值浮点时舍入不同。`gamma=None` 时 D 是整数值、除法精确，所以默认配置看不出来——第一次验证正好没覆盖到。
3. **多卡下多发了一次 `all_reduce`。** 未裁剪时 CE 分母与 loss 分母完全相同，却仍额外归约一次。**各 rank 必须在 collective 的数量和顺序上一致，这不是性能问题而是正确性问题**；而等价性验证全是单进程跑的，正好看不到它。

三条各配了测试并做**变异验证**（注入对应故障、确认测试真的会红）。`test_full_vocab_run_emits_one_denominator_all_reduce` 用 mock 分布式环境断言未裁剪发 1 次、裁剪发 2 次——这类"单进程观测不到"的性质必须显式钉住。

### 4.2 启动吞吐：双机 16 卡静默卡死 46 分钟

**症状。** 日志停在 target 权重加载之后再无任何输出，8 个进程全停在这里，`dist_timeout: 30`（30 分钟）也没有触发任何 NCCL watchdog 报错。

**定位。** 两个高价值的全局判别依据先把方向定死：其一，`dist_timeout` 是免费的分流器——超过它还静默、没有任何 watchdog 报错，说明**没有任何 rank 进入集合通信**，所有 rank 都在各自忙 CPU/IO；其二，`ps` 的 CPU TIME（`00:46:23`）≈ 墙上时间（46 分钟）、`C` 列 98–99%，说明**不是在等 IO，是在烧 CPU**。冷盘假设、rank0-only 假设、词表建图假设逐一被排除。

`py-spy dump` 定案，两个 rank 栈完全一致：

```
read (gzip.py:507) → load_feature_file (feature_store.py:205)
→ _inspect_feature_file (offline_reader.py:39) → build_offline_runtime (launch.py:567)
```

**机理。** `OfflineManifestReader` 在组装期（第一个 training step 之前）探查**每一个**特征文件，只为填 `SampleRef.feature_specs` 里的 shape/dtype。明文 `.ckpt` 走 `torch.load(mmap=True)` 只读 header，近乎免费；`.ckpt.gz` 没有随机访问，探查一个压缩样本等于把它**整个解压再丢掉**。于是启动前对全数据集做一遍串行解压，**每个 rank 各做一遍，零日志输出**。

旧版架构不会这样：组装期只 `os.walk` 列文件名，解压全发生在 `__getitem__` 里、由 DataLoader worker 进程承担、和设备计算重叠。新版把探查提前到了组装期，把这笔开销从"重叠的"变成了"串行阻塞的"，还乘了 rank 数。这是 runtime 重构（`9b9d84b`）带进来的 regression，且仓库对 `.ckpt.gz` **零测试覆盖**。

**修复。** 组装期回到纯 `os.walk`，一个文件都不打开；`SPECFORGE_VALIDATE_OFFLINE_FEATURES=1` 作为 opt-in 保留完整校验。`read()` 实测从"明文 2.3ms / gz 150ms（12 样本）"降到双双 **0.1ms**。

清空 specs 是安全的，不是猜的——三个字段的读者全查过：`num_tokens` 全仓无人读，`estimated_bytes` 只在在线 producer 的背压里用、看不到 `file://` ref，`feature_specs` 在 `FeatureDataLoader._validate_refs` 里对空 specs 显式 no-op。取张量走的是 `feature_keys`，那个永远是满的。

**一个诚实的补充：这只解决了启动那一遍。** 训练期每个样本仍要解压一次，而新版 loader 用的是 `ThreadPoolExecutor` 不是 worker 进程——zlib 的 inflate 会释放 GIL，但 `torch.load` 的反序列化和张量拷贝仍持 GIL。105MB 级样本大概率还是喂不满卡。所以操作上的结论很直接：**采集时别加 `--compress`**，或者事后 `gunzip` 掉，走 `torch.load(mmap=True)` 零解压按页读。

### 4.3 数据可训性：600k 语料里的退化样本

DSpark 采样 anchor 时要求存在位置 `i` 满足 `loss_mask[i]==1 且 loss_mask[i+1]==1`——这是上游 PR #710 新加的硬校验，旧代码宽松容忍的退化样本在新代码里直接报错：

```
ValueError: DSpark found no valid anchor with two consecutive loss tokens
```

在线路径有 `minimum_valid_tokens` 过滤，但那个参数统计的是**任意位置**的可训练 token 总数，和"相邻"是两回事；离线路径则完全没有过滤。600k 语料里"prompt 很长、assistant 很短，按 `max_length` 一截 loss token 只剩 0~1 个"的样本足够多，一个 per-rank batch 全是这种就报错。

值得一提的是**不该怎么修**：改 `_sample_anchor_positions` 遇空 batch 就跳过——FSDP 多卡下单卡跳过会导致集合通信步调不齐、HCCL 直接卡死。这是把一个显式报错换成一个静默死锁。

治本的做法是在数据侧过滤，分两层：

- `scripts/filter_trainable_conversations.py` 在**源 JSONL** 上过滤。它跑的是 SpecForge 真实的那套预处理——同一个 tokenizer、同一份 chat template、同一个 `--max-length`——然后只保留 loss mask 里有 `--min-consecutive`（默认 2）个连续可训练 token 的行。不是近似，是把训练时会发生的截断提前算一遍。
- `scripts/prepare_hidden_states.py` 补 `--minimum-valid-tokens`，把上游已有的通用过滤透传到采集阶段，让纯 prompt 行根本进不了特征目录。

### 4.4 长跑稳定性：梯度尖峰四次抹掉 4000 步

**症状。** 一次记录在案的 27B DSpark 跑在 10480 步里**四次**丢掉约 4000 步的进展：accuracy 在单个十步日志区间里从 0.55 掉到 0.15，然后花 60~820 步爬回来。

**排除。** tfevents 轨迹排除了常见嫌疑——`teacher_top1_prob`、`teacher_kept_mass`、`draft_vocab_coverage`、监督 token 数在每次起点都正常，墙上时间间隔看不到 checkpoint 停顿，也从没出现过非有限值。四次起点唯一的共同点是**梯度范数 5.6~30.1，而健康值上限是 1.5**。

**机理。** `max_grad_norm` 一次都没挡住，而且机理上挡不住：它界的是更新的**范数**，不是**方向**，而 AdamW 的逐参数步长对梯度的全局缩放近乎不变。一个被裁剪过的异常梯度仍然把每个参数朝异常方向推大约一个学习率的距离，而它留下的膨胀 `exp_avg_sq` 才是把伤害拉长到几百步"学习率被压制"的原因。

**做法。** 给梯度范数加一条控制限，超了就**整步丢弃**，Adam 的一二阶矩不动。限值是运行**几何均值的无量纲倍数**，不是绝对值——那次跑里绝对尺度自己就从 0.80 漂到 0.25，同一个固定阈值在一处是 3.8 sigma、在另一处是 8.5 sigma。

**一次失败的设计值得记下来。** 早期版本用 `exp(mu + k·sigma)`，拿记录轨迹回放只抓到四分之一：sigma 以指数形式进入限值，又被它本该检出的事件本身抬高——第一次尖峰把限值推到 525，后两次直接从底下溜过去。换成几何均值的固定倍数（10×）：

| 方案 | 4 次尖峰命中 | 858 个健康步误伤 |
|---|---|---|
| `exp(mu + k·sigma)` | 1 / 4 | 0 |
| **10 × 运行几何均值** | **4 / 4** | **0** |

回归测试钉的就是这个对比。默认关闭，开启前逐位一致（关闭时不产生任何 device-to-host 同步）；`"observe"` 模式只报告不改训练，用来在新数据集上看余量。估计量存在 optimizer state dict 里、用 `.get()` 读，老 checkpoint 照样 resume；而且与 `max_grad_norm` 相反，**改了设置故意不在 resume 时拒绝**——主要用法就是给一个已经炸过的跑中途打开它。

顺带把 AdamW 的 betas 暴露出来：`beta2=0.95` 把漏网尖峰的恢复从 ~1000 步缩到 ~20 步（`beta2=0.999` 给 `exp_avg_sq` 约 1000 步的记忆，那正是把每次事件拉长成几百步的原因）。

### 4.5 映射构建：从"不可行"到毫秒级

训练能自己建图，但只在 colocated offline 下，而且要先读完每个特征文件。gzip 下这意味着"第一步之前把整个数据集解压一遍，中间没有任何日志"，并且**每换一个 `draft_vocab_size` 就再来一遍**。这不是慢，是不可行——直接导致小词表这个功能没法调参。

`scripts/build_vocab_mapping.py` 把两半按代价切开：统计 loss-bearing token 是昂贵的、只依赖数据集，做一次并缓存（缓存键是特征文件的指纹，陈旧缓存不会被静默命中）；选 top-K 是廉价的，任意多个 K 都能从缓存里毫秒级扫出来。**而扫描恰恰是提交前最该做的事——报出来的那个比例就是接受率天花板。**

两个数据源给同样的数字：`--hidden-states-path` 读特征，精确但串行；`--data-path` 用采集时同一套 stack 重新 tokenize 源 JSONL，并行、完全不碰特征文件。后者的 tokenizer / template / max-length / 过滤参数是**必填而不是有默认值**的——默认猜错任何一个，得到的都是另一个语料的频率，而且不会报错。

两处此前"看起来像卡死"的地方：

- **映射文件的长度口径。** 映射按 **draft config 的** `vocab_size` 生成，那才是模型注册 `t2d` 的长度。`prepare_hidden_states.py` 用的是 target config 的原始 `vocab_size`，一旦 target 声明了 `padded_vocab_size` 两者就对不上，生成的文件装不进模型。
- **建图的 O(V×K) 扫描。** `process_token_dict_to_mappings` 原来把 mask 写成 `[i in used_tokens for i in range(target_vocab_size)]`，在 Python list 上做，每个 target id 一次线性扫描。V=248320 / K=64000 本机 ~42s，昇腾上几分钟，而且发生在覆盖率那行日志之后、什么都不打印的阶段——读起来就是卡死。换成把排序后的 id **scatter** 进全零 mask：**0.077s**，与旧公式在三个词表规模上逐位一致（含 dtype）。

### 4.6 评测通路：DeepSpec 侧对齐

DeepSpec 完全没有词表裁剪概念，`lm_head` 和 `markov_w2` 都按 `config.vocab_size` 建，裁剪 checkpoint 装进去会在 `markov_w2` 形状上直接挂掉。改了四处，前两处与训练侧同形：

1. `markov_head.py` — W1/W2 词表分离，`sample_block_tokens` 加 `to_target_ids` 回调；
2. `qwen3/modeling.py` — `lm_head` 按 K 建、仅裁剪时注册 buffer、`initialize_embeddings_and_head` 改成 `tgt_head[t2d]` 切行、新增 id 映射；
3. `draft_ops.py` — **读代码时发现的额外一处**：`verify_draft_tokens` 会显式校验 `draft_probs` 宽度必须等于 target 的，而且用 **target 空间的 id** 去 gather。所以要先在 K 维归一化、再散射回 V 维（裁剪外补 0）。少了这步会直接抛异常，绕过校验则会 gather 到错误的列——**这是典型的静默错误**；
4. `eval_real_dspark.py` — 原来的 `assert lm_head.weight.shape == tgt_head.shape` 在裁剪下必挂；并补读 config 顶层的 `draft_vocab_size`。

两侧键集比对是严格子集：

```
SpecForge 有、DeepSpec 无: []
DeepSpec 有、SpecForge 无: ['embed_tokens.weight', 'lm_head.weight']
同名但形状不符: 无
```

唯二多出的正是脚本里 `TIED` 已容忍并从 target 填充的两个。

target 统一为 Qwen3.6-27B（`vocab_size=248320`，64 层，`hidden_size=5120`）；草稿 5 层、`hidden_size=5120`、`block_size=16`、`markov_rank=256`、`target_layer_ids=[2,17,32,47,62]`。

| # | 词表 | 裁剪比 | 覆盖率 | seqlen | anchor | 训练数据 | 说明 |
|---|---|---|---|---|---|---|---|
| **A** | 全词表 248320 | 1× | 100% | 2048 | 512 | 600k 通用 | 基线 |

| **C** | 64000 | 3.88× | 98.9% | 4096 | 1024 | 600k 通用 | Markov 头 80.0M |

另需注意：B/C 的覆盖率是在 600k **通用**语料上统计的。D 用的是领域数据，若后续做领域小词表，覆盖率必须在领域语料上重新统计——**领域 token 分布与通用语料不同时，实际接受率天花板会低于这两个数字**。

## 7. 总结与展望

本文记录了在昇腾上为 Qwen3.6-27B 训练 DSpark 草稿模型的完整路径。与业界既有实践相比，本工作的差异化在于**离线特征 + 词表裁剪**这条组合：为 SpecForge 的 DSpark 补上此前被架构契约明确禁止的词表裁剪能力（248320 → 64000 / 32000，objective 段显存 2.18×，Markov 头 127.4M → 80.0M / 71.8M），并在打通过程中定位修复了十余项在真实数据规模下才暴露的问题——其中离线 reader 的启动期回归是最典型的一例：它在小数据集上完全不显形，在 600k × 双机 16 卡上表现为静默卡死 46 分钟。

目前已产出 4 个草稿模型，基准评测与 MTP 对比进行中。

## 彩蛋：三次被证伪的"不变"

这次工作里最有价值的一条经验，不是词表裁剪本身，而是"未裁剪路径不变"这个承诺**被证伪了三次**。

第一次是我们自己写的回归测试。它用同一 seed 在**同一分支上**建两个模型互比——只证明了初始化可复现，完全不能证明新实现与旧目标一致。**而我们在开发文档里已经据此写下了"unpruned 逐位不变、有测试守着"的结论。** 这条比没有测试更糟，因为它提供的是虚假的安全感。修法是在测试里**逐字转写**旧公式作为参照实现，按名字逐项 bit-exact 比对，参照函数是冻结的——由实现生成的参照检测不出实现的变化。

从那以后每个测试都做**变异验证**：注入对应故障，确认测试真的会红。不做这一步就不能说"有测试守着"。

第二次和第三次是差分测试查出来的：`loss_decay_gamma` 非空时的浮点舍入差异，以及多卡下多发的那一次 `all_reduce`。后者尤其值得说——**单进程验证证明不了分布式性质**。多出来的那次归约、resume contract 新增的那个 key（它已经在真实的 8 卡 NPU 集群上炸过一次），在单机单进程下完全看不见。凡是涉及 collective 序列、checkpoint 契约、跨 rank 一致性的改动，要么用 mock 显式钉住，要么就承认没验证过。

这两条的共同点是：**结论的强度必须匹配证据的强度。**"在我跑过的检查下未检出差异"和"无 bug"，是两句不同的话。
