## 3. 本地适配原来增加了什么

### 3.1 DSpark 词表裁剪

DSpark 现在可以通过 draft config 顶层的 `draft_vocab_size` 使用小于 target vocabulary 的 draft vocabulary。

主要实现包括：

- 新增统一的 `DraftVocabMappingMixin`
- 注册、安装和验证 `t2d`、`d2t` 映射
- `markov_w1` 保持 target 全词表，`markov_w2` 按 draft vocabulary 输出
- target token label 映射到 draft id，裁剪外 token 使用专用 ignore label
- objective 的 target head 按映射裁剪
- 映射版本变化时自动失效并重建裁剪 head 缓存
- offline 和 streaming DSpark 都声明支持 vocabulary mapping
- 全词表运行不注册额外 mapping buffer，保持旧 checkpoint 兼容

### 3.2 词表裁剪相关 bug 修复

本地分支在实现后又连续修复了多处正确性问题：

1. **裁剪 checkpoint 重新加载后误报 mapping 未安装**

   原因是 mapping 状态最初依赖安装函数设置的普通标志，但 `load_state_dict` 不会调用该函数。最终改为从持久化 buffer 派生加载状态。

2. **同尺寸但内容不同的 mapping 可以静默替换**

   这会让相同 draft id 指向不同 target token。现在 resume 或重复安装时会校验映射内容，不一致直接拒绝。

3. **接受率在裁剪后被系统性高估**

   原实现使用了在保留 vocabulary 上重新归一化的 teacher distribution 计算 acceptance。现在蒸馏仍使用条件分布，但 acceptance 使用 target 的真实保留概率质量。

4. **被裁掉的硬标签仍进入 CE 分母**

   现在裁剪外 label 同时退出 CE 分子和分母，避免 CE 权重随 vocabulary coverage 漂移。

5. **未裁剪运行的 checkpoint resume contract 被改变**

   `dspark_draft_vocab_size` 现在只在实际裁剪时写入，旧全词表 checkpoint 不会因为缺少新字段而无法恢复。

6. **未裁剪 objective 浮点运算顺序发生变化**

   在 `loss_decay_gamma` 非空时，拆分分母会产生浮点舍入差异。全词表路径恢复了旧公式的单分母表达式。

7. **未裁剪多卡运行多出一次 collective**

   全词表 CE 分母与总 loss 分母相同，现在直接复用，只在实际裁剪时增加第二次归约。

### 3.3 数据准备和 vocabulary mapping 工具

新增了：

- `scripts/build_vocab_mapping.py`
- `scripts/filter_trainable_conversations.py`
- 从 source JSONL 或已有 hidden features 统计有效 token 频率
- 流式计数，避免一次性加载完整数据列
- token count 磁盘缓存和 corpus identity 校验
- 直接生成 mapping，无需重新生成 hidden states
- `t2d` 从逐 token 列表扫描改成 tensor scatter
- `--dataset-cache-dir` 下固定 conversation cache，避免缓存位置漂移
- `--minimum-valid-tokens`，过滤截断后没有足够监督 token 的样本

### 3.4 梯度尖峰保护

新增 `off`、`observe`、`on` 三种梯度尖峰模式：

- `observe` 只观测并记录，不改变原训练结果
- `on` 可以跳过异常 optimizer step，而不是把异常梯度简单裁剪到阈值
- 使用历史梯度范数的几何均值构建相对阈值
- 非有限梯度可以在 warmup 阶段直接拦截
- 连续跳步带熔断和重新基线逻辑，避免配置错误导致永久冻结
- guard 状态进入 checkpoint，同时兼容没有该状态的旧 checkpoint

## 5. 实际发生的 5 个文本冲突

### 5.1 `scripts/prepare_hidden_states.py`

**双方改动：**

- 本地：抽出 `build_processed_dataset`，加入 `--minimum-valid-tokens`
- 社区：加入算法提供的 `loss_mask_filter`，并在 filter 后再应用 `num_samples`

**错误解决方式的风险：**

- 只选本地版本会丢失 DSpark/DFlash 的相邻监督 token 过滤
- 只选社区版本会丢失用户显式配置的最小有效 token 阈值

**最终解决：**

保留 `build_processed_dataset`，增加 `loss_mask_filter` 参数，同时向 `build_eagle3_dataset` 传递：

- `minimum_valid_tokens=args.minimum_valid_tokens`
- `loss_mask_filter=capture_plan.loss_mask_filter`

社区的 filter 后采样和空数据集校验也被保留。

**功能结论：** 两类过滤均有效，没有互相覆盖。新增了专门回归测试验证两个参数可以同时透传。

## 7. 扩大测试发现的语义冲突

### 7.1 问题表现

社区新增测试 `test_dspark_uses_its_dedicated_server_capture_method` 使用一个 mock 的 `dspark-draft` 配置路径，目的是验证 DSpark 使用独立的 capture method。

本地 `_prunes_vocabulary` 在 draft config 无法读取时采用了保守策略：直接返回 `True`。这会将“配置尚未解析”误判为“已启用 vocabulary pruning”，进而提前报错：

```text
DSpark disaggregated runs require model.vocab_mapping_path
```

这不是社区功能本身的问题，而是两条开发线组合后才出现的验证顺序冲突。

### 7.2 解决方式

现在 draft config 无法读取时，`_prunes_vocabulary` 返回 `False`：

- 无法解析配置不再被当作启用裁剪的证据
- 按代码路径分析，真正的配置加载错误会继续在后续 model-loading 边界按原始原因报出；本次没有为该报错顺序增加完整端到端测试
- 能正常解析且 `draft_vocab_size < vocab_size` 的配置仍被识别为裁剪
- 裁剪的 disaggregated run 仍强制要求显式共享 mapping
- 全词表 DSpark disaggregated run 不要求 mapping

新增回归测试固定上述行为。

### 7.3 是否削弱了安全保护

没有削弱已知裁剪配置的保护。变化只针对“配置根本无法解析”的情况，避免用一个猜测出的 pruning 状态遮蔽真正的 config error。

## 10. 剩余风险

### 10.1 高风险：部署端 patch 必须同步

社区将 DSpark server capture 独立为 `dspark` method，并更新了 SGLang 0.5.14、Ascend 和 Kimi-K3 patch。训练代码升级而 capture server 仍使用旧 patch 时，最可能出现 method 不识别、返回字段不匹配或异步协议不一致。

### 10.2 高风险：硬件后端没有交叉验证

最终模型公共路径同时包含 vocabulary pruning、sliding window 和 FlexAttention。CPU objective 测试只能证明 Python 语义，不能替代 NPU/ROCm/CUDA kernel 验证。

### 10.3 中风险：训练数值基线会发生合理变化

社区修复了 anchor 选择、partial tail 和跨 DP loss normalization。即使未启用 vocabulary pruning，新分支训练曲线也可能与旧本地分支不同。这属于社区正确性修复带来的行为变化，不应直接判为回归，但需要重新建立 loss/accuracy 基线。

### 10.4 中风险：resume 契约更严格

- 裁剪 checkpoint 必须使用同一份 mapping
- 全词表 checkpoint 不能直接恢复到小词表模型
- scheduler 类型改变时 resume 会被拒绝
- grad guard 状态可兼容旧 checkpoint，但启用后会改变 optimizer step 是否执行

### 10.5 中风险：大规模数据和长序列资源消耗

Kimi-K3 recipe、64K sequence、全词表 teacher normalizer 和 Mooncake resident watermark 都会显著放大内存、网络和存储需求。配置可以解析不代表资源规模已经适合现有集群。

## 11. 建议的上线验证顺序

1. 在目标 SGLang 版本上重新应用对应 patch，启动 capture server smoke test。
2. 用全词表 DSpark 做 10～50 step 单卡/单机回归，确认旧路径 loss 和吞吐。
3. 用小 vocabulary 做同数据短跑，检查 `draft_vocab_coverage` 和 `teacher_kept_mass`。
4. 做 checkpoint save/resume，并验证 mapping identity 拒绝逻辑。
5. 启用多卡，检查 collective、global loss normalization 和 grad guard 日志。
6. 再进入 Mooncake、多节点或 NPU/ROCm 环境。
7. 最后验证 Kimi-K3/长序列 recipe，避免同时引入模型、协议和资源规模三个变量。

## 12. 最终判断

本次合入在提交结构上完整，并且当前已覆盖的 CPU 路径回归通过：本地适配没有被社区代码覆盖，社区新功能也没有为了迁就本地实现而被回退。5 个文本冲突均以组合双方行为的方式解决，自动合并区域也经过语义复核；测试进一步发现并修复了 1 个只有合并后才出现的 validation-order 问题。

因此，`0812_upstream` 可以作为后续统一验证分支。当前不能给出的承诺是“所有硬件和分布式部署已经全量验证”。在完成目标集群 smoke test、短训练、resume 和多卡验证前，应将它视为**提交完整、当前核心回归通过、硬件集成待验证**的候选分支。
