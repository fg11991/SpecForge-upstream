## 0. 三句话

1. 上游 SpecForge 能训 DSpark,但**训不了我们这个规模的这个数据集**:600k 语料里的退化样本会让训练直接报错,gzip 特征会让启动静默卡 46 分钟,27B 全词表的 Markov 头显存吃不消,长跑还会被梯度尖峰打回四千步。适配做的是把这四件事一件件拆掉。
2. 主体改动是给 DSpark 补上**词表裁剪**——这是上游有契约明确禁止、而参照实现(speculators)从第一版就有的能力。开关只有一行:draft config 顶层的 `"draft_vocab_size"`。
3. 规模:生产代码 `+2852 / −88`,测试 `+1984 / −19`,42 个文件。目前跑出 4 个模型(1 全词表 / 2 小词表 / 1 领域微调),评测进行中。

## 1. 起点:上游给了什么,缺什么

上游 `sgl0514` 已经把 DSpark 原生并入新架构(`algorithms/` + `specforge train --config yaml`),NPU 底座也合了一部分(设备自动探测 #559、Ascend distributed 后端 #584)。走离线路径还顺带绕开了 sglang capture 那一大块昇腾适配——末层 hidden 已经在特征文件里。

所以起点不差。真正缺的是下面这些,全部是"上游在小数据集/小模型上跑得通,换到我们这个组合就断"的那类缺口:

| 缺口 | 上游现状 | 我们撞上的形态 |
|---|---|---|
| anchor 需要**相邻两个** loss token | PR #710 加了硬校验,但离线路径没有对应过滤 | `ValueError: DSpark found no valid anchor with two consecutive loss tokens`,训练起不来 |
| 离线 reader 在组装期探查每个特征文件 | `.ckpt` 走 mmap 只读 header;`.ckpt.gz` 必须整份解压 | 启动后静默 46 分钟,零日志,每个 rank 各付一遍 |
| DSpark 只有全词表 | `supports_vocab_mapping=False`,是被测试保护的架构契约 | V=248320 的 `[B,N,K,V]` logits + 127M 的 Markov 头 |
| 词表映射只能从特征反推 | 训练时自动建图要读完整个数据集 | 换一个 K 就得重扫一遍;`--compress` 下等于重新解压全量 |
| 梯度尖峰无防护 | 只有 `max_grad_norm` | 10480 步里四次把 accuracy 从 0.55 砸到 0.15 |
| 评测侧(DeepSpec)不认裁剪权重 | `lm_head` / `markov_w2` 都按 `config.vocab_size` 建 | 加载即形状不符 |

## 2. 适配做了什么

### 2.1 数据侧:让 600k 语料真的能进训练

DSpark 采样 anchor 时要求存在位置 `i` 满足 `loss_mask[i]==1 且 loss_mask[i+1]==1`。上游在线路径靠 `minimum_valid_tokens` 过滤,但那个参数统计的是**任意位置**的可训练 token 总数,和"相邻"是两回事;离线路径则完全没有过滤。600k 语料里"prompt 很长、assistant 很短、按 `max_length` 一截 loss token 只剩 0~1 个"的样本足够多,一个 per-rank batch 全是这种就报错。

处理分两层:

- `scripts/filter_trainable_conversations.py`(新增 324 行)在**源 JSONL** 上过滤。它跑的是 SpecForge 真实的那套预处理——同一个 tokenizer、同一份 chat template、同一个 `--max-length`——然后只保留 loss mask 里有 `--min-consecutive`(默认 2)个连续可训练 token 的行。不是近似,是把训练时会发生的截断提前算一遍。
- `scripts/prepare_hidden_states.py` 补 `--minimum-valid-tokens`,把上游已有的那道通用过滤透传到采集阶段,让纯 prompt 行根本进不了特征目录。

顺带修了两个在这个数据量下才显形的问题。一是 `Dataset.from_generator` 没有传 `cache_dir`,原始对话的 arrow 缓存落在 `~/.cache/huggingface`,而 tokenize 后的缓存落在用户指定的目录——600k 条足以把 home 分区写满。二是 `count_dataset_tokens` 直接读 `dataset["input_ids"]`,把整个语料一次性物化成 Python int,几十 GB,而且发生在最后一个进度条走完之后,看起来就是"卡在 Tokenized N samples 然后 OOM"。改成按 batch 流式 + 每批一次 `bincount`,原来的内层循环是每个 (样本, 不同 token) 走一次,换成同样算术的十亿分之一次迭代。

### 2.2 启动期:离线特征读取从 46 分钟回到秒级

现场是 2 节点 × 8 卡,日志停在 target 权重加载之后再无输出,`dist_timeout: 30` 也没触发 NCCL watchdog。`py-spy dump` 直接定案:

```
read (gzip.py:507) → load_feature_file (feature_store.py:205)
→ _inspect_feature_file (offline_reader.py:39) → build_offline_runtime (launch.py:567)
```

`OfflineManifestReader` 在组装期探查每一个特征文件,只为填 `SampleRef.feature_specs` 里的 shape/dtype。明文走 `torch.load(mmap=True)` 近乎免费,gz 没有随机访问,探查一个样本等于把它整个解压再丢掉。旧版架构不会这样——旧版组装期只 `os.walk` 列文件名,解压全在 `__getitem__` 里由 DataLoader worker 承担、和计算重叠。这是 runtime 重构(`9b9d84b`)带进来的 regression,而且仓库对 `.ckpt.gz` 零测试覆盖。

改回旧版语义:组装期只列文件名,一个文件都不打开;`SPECFORGE_VALIDATE_OFFLINE_FEATURES=1` 作为 opt-in 保留完整校验。`read()` 从"明文 2.3ms / gz 150ms"降到双双 0.1ms(12 样本)。

清空 specs 是安全的,不是猜的:三个字段的读者全查过——`num_tokens` 全仓无人读,`estimated_bytes` 只在在线 producer 的背压里用、看不到 `file://` ref,`feature_specs` 在 `FeatureDataLoader._validate_refs` 里对空 specs 显式 no-op。取张量走的是 `feature_keys`,那个永远是满的。

代价是 key 缺失从"组装期报错"变成"首次访问时报错",所以 opt-in 那条路必须留着,否则它就是死代码。

> 注意:这只解决了启动那一遍。训练期每个样本仍要解压一次,而新版 loader 用的是 `ThreadPoolExecutor` 不是 worker 进程——`torch.load` 的反序列化持 GIL。105MB 级样本大概率还是喂不满卡。**实践上直接 `gunzip` 掉,采集时别加 `--compress`。**

### 2.3 词表裁剪(主体改动)

DSpark 原论文的设计是"共享冻结的 target lm_head + 全词表",SpecForge 忠实实现了,连 `t2d`/`d2t` buffer 都没有。参照实现 speculators 从 DSpark 第一版(#677)就带着裁剪,已发布的 `novita/kimi-k2.6-dspark` 就是 163840→32000。所以这不是"要不要做",是"上游缺了一块"。

对着 speculators 读出来两点是自己不一定能想到的:

**W1 和 W2 不共享词表。** `W1` 由**上一个真实 token** 索引,那个 token 可以是任意 target id,必须保持全词表;`W2` 的输出要叠到 draft logits 上,所以跟随裁剪。SpecForge 原本两边都用 `self.vocab_size`。

**裁剪不会让 draft"学得更难",反而更容易。** 教师和学生被施加了完全相同的限制——`lm_head` 和 `verifier_lm_head` 是同一份 target lm_head 按同一个 `t2d` 切出来的行,损失在 K 维 softmax,教师分布也被限制并重归一化了。学生要拟合的是 `p|_K`,去掉的是长尾上几乎学不出来也几乎采不到的那部分质量。

真正的代价只有一个,而且是硬上界:**任何落在 draft 词表外的 target token,draft 永远提不出来,那个位置必然被拒。接受率天花板 ≈ 训练分布下的 top-K 覆盖率。** 所以覆盖率必须出现在训练日志里(`draft_vocab_coverage`),而不是事后审计。

实现上分层:

| 层 | 改动 |
|---|---|
| 模型 | 新增 `modeling/draft/vocab_mixin.py::DraftVocabMappingMixin`,统一 `t2d`/`d2t` 的注册、安装、校验与派生查找表;`Eagle3DraftModel` 也混入它,删掉重复的 `load_vocab_mapping` |
| 模型 | `DFlashDraftModel` 混入 mixin,新增 `draft_logits_from_target_head` / `draft_ids_to_target_ids` |
| 模型 | `VanillaMarkovHead` 的 `markov_w1` 保持 `vocab_size`,`markov_w2` 改用 `draft_vocab_size`,三种 head 类型都透传 |
| 目标 | `_dspark_objective_chunk_terms` 用按 `t2d` 切行的头;硬标签映射到 draft 空间,越界的记 `OUT_OF_DRAFT_VOCAB_LABEL` |
| 契约 | `dspark/providers.py` 补 `supports_vocab_mapping=True` + `vocab_mapping_modes={OFFLINE, STREAMING}` |
| 校验 | `application/planning.py` 新增两条拒绝规则:算法不支持 mapping 却给了路径;支持但本次不裁剪却给了路径 |

三个决定值得单独记:

**惰性切头 + 版本号缓存。** 训练模型在 `build_model_bundle` 里就构造好了,但 t2d/d2t 要到 `_ensure_offline_vocab_mapping` 才装上。所以裁剪头必须首次使用时才切,并按 draft 模型的 `vocab_mapping_version` 做缓存键,否则后装的映射不生效。

**`vocab_mapping_loaded` 做成从 buffer 派生的 property,不是安装时置位的标志。** buffer 也会经由 `load_state_dict` / `from_pretrained` 进来,那两条路径不调用我们的任何方法。做成标志位的话,一个正确保存的裁剪 checkpoint 重新加载后会报告"没装映射"然后拒绝运行。`bool(t2d.any())` 一劳永逸——全零的初始 buffer 正是"还没装"的无歧义状态。

**不裁剪时不注册 buffer。** 无条件注册会给所有存量全词表 checkpoint 的 state dict 加两个键,而 warm start 把缺失键当致命错误。藏在 `use_draft_vocab` 后面,存量 checkpoint 逐字节可加载。

#### 和 speculators 的一处实质差异

speculators 是纯软分布蒸馏,SpecForge 的 DSpark 是**混合目标**:硬标签 CE(α=0.1)+ 软分布 L1(α=0.9)+ confidence BCE。硬标签这条 speculators 没有,所以裁剪时多一道工序——`target_ids` 是 target 词表的真实 id,必须经 `t2d` 映射到 draft 空间,落在词表外的排除。这一步不能省,否则就是"标签越界 / 指向错误行"的静默 bug。而且 CE 拿了自己的分母:被裁的标签同时退出分子和分母,否则 `alpha_ce` 会随覆盖率漂移。L1 项继续用全部监督位置,它的教师在每个位置都有定义。

#### 接受概率:一个必须分开的教师

裁剪后教师分布在 K 维重新归一化,原来的 `accept_probability = 1 - 0.5·L1(q, p̃)` 会**系统性偏高**——真实接受率用的是未归一化的 `p_i`,而 `p̃_i = p_i/Σ_K p ≥ p_i`。review 给的反例:target 在 4 个 token 上均匀、K 只留 2 个、draft 恰好等于条件分布,当前代码算 1.0,真值 0.5。关键在于**未裁剪时这个量本来就是精确 speculative decoding 的接受率**,所以裁剪静默改了它的语义,是回归而不只是不精确。

修法是把两个教师分开,合并任何一边都是错的:

| 用途 | 教师 | 理由 |
|---|---|---|
| L1 蒸馏损失(α=0.9) | `p̃`,在 K 上重归一化 | draft 物理上无法在 K 外放质量,其分布在 K 上必然和为 1。目标若用和为 `m<1` 的真实 `p`,损失会有 `1−m` 的不可约下界并整体压偏梯度 |
| `accept_probability` | 真实 `p`,和为 `m ≤ 1` | 它是对服务端接受率的**预测**(喂 confidence head 的 BCE 目标和 `tau_probabilistic`)。被裁掉的概率质量在服务时是真实的拒绝 |

全词表归一化因子用 `_full_vocab_logsumexp()` 分块求:按词表走 `lm_head.weight`,每块立即 `logsumexp` 归约成标量,再用可结合性合并。裁剪要避免的 `[..., V]` 张量始终没被物化,调用点在 `no_grad` 内。新增指标 `teacher_kept_mass` 界的是**单步**接受概率,不是 `tau_probabilistic` 的上界(后者含 anchor token 和累积乘积)。

#### "未裁剪路径不变"被证伪了三次

上线前提是:不开小词表时行为与基线完全一致。基于单元测试下的这个结论**三次都不成立**,三次都是差分测试查出来的——同一脚本在两个 worktree 各跑一次,对 loss、accuracy、全部 ratio metrics 的分子分母、以及全部梯度做 sha256 逐位比对,覆盖 4 种配置。

1. **resume contract 多了一个 key,已在真机上炸过。** 无条件写入 `dspark_draft_vocab_size` 会让本功能之前产出的**所有** DSpark checkpoint 无法 resume(`trainer.py` 对"契约里有、checkpoint 里没有"的 key 硬报错)。真实报错:`ValueError: checkpoint ...-step10000 does not record required algorithm resume semantic dspark_draft_vocab_size`。改成仅在 `use_draft_vocab` 时写入。
2. **`loss_decay_gamma` 非空时最终 loss 不逐位相同。** 把 loss 拆成两个分母分别相除后,`x/D + y/D` 与 `(x+y)/D` 在 D 为非整数浮点时舍入不同。`gamma=None` 时 D 是整数值、除法精确,所以默认配置看不出来。未裁剪路径改回单分母表达式。
3. **多卡下多发了一次 `all_reduce`。** 未裁剪时 CE 分母与 loss 分母完全相同,却仍额外归约一次。各 rank 必须在 collective 的数量和顺序上一致,这是正确性问题不是性能问题;而等价性验证全在单进程跑,正好看不到。

三条各配了测试并做变异验证。`test_full_vocab_run_emits_one_denominator_all_reduce` 用 mock 分布式环境断言未裁剪发 1 次、裁剪发 2 次——这类"单进程观测不到"的性质必须显式钉住。

#### 显存

实测(CPU fp32,V=151936、K=32000、block=7、chunk=128 blocks=896 token):

| 配置 | objective 段分配 | 相对 |
|---|---|---|
| 全词表 | 5.874 GiB | 1.00× |
| 裁剪 K=32000 | **2.690 GiB** | **2.18×** |
| 裁剪 K=32000(若不做接受率修正) | 2.477 GiB | 2.37× |

H=256 与 H=1024 两次测得比值都是 2.18×,说明该段由词表维张量主导、比值不随 hidden size 变化。

几点必须说清楚:

- 早期分析文档里写的 4.75× 是**错的量纲**,那是 `[B,N,K,V]` 单个 logits 张量的比值,不是 objective 段的整体比值。confidence head、markov 的 rank 维中间量、hidden 相关张量都不随词表缩小。
- 接受率修正的显存代价只有 +0.21 GiB(+8.6%),比预估小得多,因为分块后立即归约。
- **新增固定开销**:裁剪头拷贝 ≈ `K × H × dtype_bytes`。27B(H=5120)推算 K=64000 时 bf16 约 655 MB、K=32000 约 327 MB,且修正之后 `self.lm_head` 全量权重不能释放(算归一化因子要用)。这是推算,未实测。
- 参数侧是干净收益,Markov 头 127.4M → 80.0M(K=64000)/ 71.8M(K=32000),只有 W2 缩小。推算,未实测。

### 2.4 词表映射的构建链路

训练能自己建图,但只在 colocated offline 下、而且要先读完每个特征文件。gzip 下这意味着"第一步之前把整个数据集解压一遍,中间没有任何日志",并且**每换一个 `draft_vocab_size` 就再来一遍**。这不是慢,是不可行——直接导致小词表这个功能没法调参。

`scripts/build_vocab_mapping.py`(新增 452 行)把两半按代价切开:统计 loss-bearing token 是昂贵的、只依赖数据集,做一次并缓存(缓存键是特征文件的指纹,陈旧缓存不会被静默命中);选 top-K 是廉价的,任意多个 K 都能从缓存里毫秒级扫出来。而扫描恰恰是提交前最该做的事——报出来的那个比例就是接受率天花板。

两个数据源给同样的数字:`--hidden-states-path` 读特征,精确但串行;`--data-path` 用采集时同一套 stack 重新 tokenize 源 JSONL,并行、完全不碰特征文件。后者的 tokenizer / template / max-length / 过滤参数是**必填而不是有默认值**的——默认猜错任何一个,得到的都是另一个语料的频率。

还有两处此前是"看起来像卡死"的地方:

- 映射文件按 **draft config 的** `vocab_size` 生成,那才是模型注册 `t2d` 的长度。`prepare_hidden_states.py` 用的是 target config 的原始 `vocab_size`,一旦 target 声明了 `padded_vocab_size` 两者就对不上,生成的文件装不进模型。
- `process_token_dict_to_mappings` 原来把 mask 写成 `[i in used_tokens for i in range(target_vocab_size)]`,在 Python list 上做,每个 target id 一次线性扫描。V=248320 / K=64000 本机 ~42s,昇腾上几分钟,而且发生在覆盖率那行日志之后、什么都不打印的阶段。换成把排序后的 id **scatter** 进全零 mask:0.077s,逐位一致。

### 2.5 训练稳定性:丢弃梯度尖峰步

一次 27B DSpark 记录跑在 10480 步里**四次**丢掉约 4000 步的进展:accuracy 在单个十步日志区间里从 0.55 掉到 0.15,然后花 60~820 步爬回来。tfevents 排除了常见嫌疑——`teacher_top1_prob`、`teacher_kept_mass`、`draft_vocab_coverage`、监督 token 数在每次起点都正常,墙上时间间隔看不到 checkpoint 停顿,也从没出现过非有限值。四次起点唯一的共同点是**梯度范数 5.6~30.1,而健康值上限是 1.5**。

`max_grad_norm` 一次都没挡住,而且挡不住:它界的是更新的范数不是方向,AdamW 的逐参数步长对梯度的全局缩放近乎不变。被裁剪过的异常梯度仍然把每个参数朝异常方向推大约一个学习率,而它留下的膨胀 `exp_avg_sq` 才是把伤害拉长到几百步的原因。

做法是给梯度范数加一条控制限,超了就**整步丢弃**,Adam 的一二阶矩不动。限值是运行几何均值的无量纲倍数,不是绝对值——那次跑里绝对尺度自己就从 0.80 漂到 0.25,固定阈值在一处是 3.8 sigma、在另一处是 8.5 sigma。

早期版本用 `exp(mu + k·sigma)`,拿记录轨迹回放只抓到四分之一:sigma 以指数形式进入限值,又被它本该检出的事件本身抬高,第一次尖峰把限值推到 525,后两次直接从底下溜过去。换成几何均值的固定倍数,**4/4 全抓,858 个健康步一个没误伤**。回归测试钉的就是这个对比。

默认关闭,开启前逐位一致(关闭时不产生任何 device-to-host 同步);`"observe"` 模式只报告不改训练,用来在新数据集上看余量。估计量存在 optimizer state dict 里,用 `.get()` 读,老 checkpoint 照样 resume;而且和 `max_grad_norm` 不同,**改了设置故意不在 resume 时拒绝**——本来就是要能给一个已经炸过的跑打开它。顺带把 AdamW 的 betas 暴露出来:`beta2=0.95` 把漏网尖峰的恢复从 ~1000 步缩到 ~20 步。

### 2.6 评测侧(DeepSpec)对齐

DeepSpec 完全没有词表裁剪概念,裁剪 checkpoint 装进去会在 `markov_w2` 形状上直接挂掉。改了四处,前两处与训练侧同形:

1. `markov_head.py` — W1/W2 词表分离,`sample_block_tokens` 加 `to_target_ids` 回调
2. `qwen3/modeling.py` — `lm_head` 按 K 建、仅裁剪时注册 buffer、`initialize_embeddings_and_head` 改成 `tgt_head[t2d]` 切行、新增 id 映射
3. `draft_ops.py` — **读代码时发现的额外一处**:`verify_draft_tokens` 会显式校验 `draft_probs` 宽度必须等于 target 的,而且用 **target 空间的 id** 去 gather。所以要先在 K 维归一化、再散射回 V 维(裁剪外补 0)。少了这步直接抛异常,绕过校验则会 gather 到错误的列
4. `eval_real_dspark.py` — 原来的 `assert lm_head.weight.shape == tgt_head.shape` 在裁剪下必挂;并补读 config 顶层的 `draft_vocab_size`

两侧键集比对是严格子集:

```
SpecForge 有、DeepSpec 无: []
DeepSpec 有、SpecForge 无: ['embed_tokens.weight', 'lm_head.weight']
同名但形状不符: 无
```

唯二多出的正是脚本里 `TIED` 已容忍并从 target 填充的两个。

## 4. 什么情况下会失效

### 算法固有上界(消不掉,只能知道在哪)

**落在 draft 词表外的 target token 必然被拒。** 单步接受概率的上界就是 `teacher_kept_mass`,整体接受率的上界 ≈ 训练分布下 top-K 的覆盖率。K=32000 是 95.8%,意味着约 4.2% 的位置天然提不出正确 token;K=64000 是 98.9%,约 1.1%。**这条上界在服务端表现为接受长度封顶,不会有任何报错。**

覆盖率是按训练语料统计的。领域数据的 token 分布若与通用语料不同,实际覆盖率会低于这两个数字——领域微调模型尤其要单独统计一次。

### 会显式报错(能诊断)

| 触发条件 | 报错关键词 |
|---|---|
| 裁剪运行 resume 全词表 checkpoint | `markov_w2` 形状不符 / 缺失 buffer 键 |
| resume 时换了词表映射 | 拒绝 resume(`2b19e27`) |
| 算法不支持 mapping 却给了 `vocab_mapping_path` | planning 阶段拒绝 |
| 支持 mapping 但本次不裁剪却给了路径 | planning 阶段拒绝 |
| 映射文件长度按 target config 的 `vocab_size` 生成、而 target 有 padding | 装载 `t2d` 时长度不符 |
| batch 内无相邻两个 loss token | `no valid anchor with two consecutive loss tokens` |

### 会静默失效(重点)

| 情形 | 后果 | 怎么确认没发生 |
|---|---|---|
| yaml 里设了 `model.vocab_mapping_path` | 走显式文件,**跳过自动建图**,可能用的是另一份语料统计出的映射 | 检查 prepare/训练日志里的 `top K token frequency ratio` 是否与预期一致 |
| `--data-path` 的 tokenizer/template/max-length 与采集时不一致 | 频率来自另一个语料,映射错但训练照跑 | 参数必填,但**没有交叉校验**;需人工核对与 `prepare_hidden_states.py` 同参 |
| 硬标签未经 `t2d` 映射 | 标签指向错误行,loss 有值但学错东西 | `draft_vocab_coverage` 出现在日志里即说明裁剪路径生效 |
| 接受概率用重归一化教师 | `tau_probabilistic` / confidence head 目标系统性偏高 | `teacher_kept_mass` 与 `accept_probability` 同时看,后者不应超过前者 |
| SGLang 侧不消费 `d2t` | 裁剪权重上线后**输出错 token id** | **目前没有确认手段**,见 §9 |

### 有意为之的保守取舍

- **小词表必须从头训**,不能从全词表 checkpoint warm start。`markov_w2` 输出维从 V 变 K,形状对不上,而且裁剪模型多两个 buffer。裁剪运行 resume 全词表 checkpoint 被拒是正确行为。
- **梯度尖峰守卫默认关闭**,`observe` 先看余量再开。误跳一步的代价远小于误放一次尖峰,但在新数据集上限值倍数需要重新确认。
- **改设置在 resume 时故意不拒绝**(与 `max_grad_norm` 相反),因为主要用法就是给一个已经炸过的跑中途打开它。

## 5. 证据强度

### 有测试守着,且做过变异验证

- 未裁剪路径与基线**逐位一致**(loss / accuracy / 全部 ratio metrics / 全部梯度 sha256),覆盖 4 种配置。参照实现是**逐字转写**基线旧公式的冻结函数——由实现生成的参照检测不出实现的变化。
- 未裁剪发 1 次分母 `all_reduce`、裁剪发 2 次(mock 分布式环境)。
- 梯度尖峰逻辑的 **9 种变异全部转红**;控制限对记录轨迹 4/4 命中、858 健康步 0 误伤。
- 组装期不打开任何文件:把 `torch.load` 和 `gzip.open` 都 patch 成抛异常,断言 `read()` 期间一次都没被调到(明文和 gz 分别测)。
- t2d scatter 构建与旧公式在三个词表规模上逐位一致(含 dtype)。
- 流式 token 统计:断言不发生整列读取,换回列访问会红。

### 只是读代码核对,未实测

- FSDP 下 `lm_head` / `embed_tokens` 在 `training/backend.py:173` 被显式放进 `ignored_modules`、不分片,所以 `_full_vocab_logsumexp` 取全量权重是安全的。**读代码确认,非实测。**
- Markov 头参数量 127.4M → 80.0M / 71.8M,裁剪头拷贝 655 MB / 327 MB(bf16, H=5120)。**推算。**

### 没验证

- **多卡 / 多机没实测。** collective 序列有 mock 测试钉住,真机没跑过对拍。
- **NPU 上的布尔行索引没验证。** `_pruned_head_state` 的 `weight[mask]`、DeepSpec 的 `tgt_head[mask]` 和 `full[..., kept] = probs` 都是布尔索引/索引赋值,Ascend 是否支持未确认。`draft_vocab_index()` 已经规避(挪到 CPU 构建),这几处没有。
- **DeepSpec 侧只在 CPU 小模型上跑通过 propose→verify**,没跑过真实 27B。
- **显存数字是 qwen3-8b 形状(V=151936/K=32000)在 CPU fp32 上测的**,不是 27B 实测。

上机验收建议的顺序:先对拍中间态(键集比对 → 覆盖率日志 → `teacher_kept_mass`/`accept_probability` 的相对关系),再看端到端接受长度。端到端正常会掩盖中间环节的错误。

| # | 词表 | 覆盖率 | seqlen | anchor | 数据 | 说明 |
|---|---|---|---|---|---|---|
| A | 全词表 248320 | 100% | 2048 | 512 | 600k 通用 | 基线 |
| B | 32000 | 95.8% | 4096 | 1024 | 600k 通用 | 7.76× 裁剪 |
| C | 64000 | 98.9% | 4096 | 1024 | 600k 通用 | 3.88× 裁剪 |

## 9. 遗留与风险

按风险排序:

1. **SGLang 的 DSpark 推理内核是否消费 `d2t` —— 未确认,硬阻塞。** 训练端做完但服务端不认,裁剪权重上线即输出错 token id,而且没有正向确认手段。`export/to_sglang.py` 第一行就 `if strategy != "eagle3": raise`,DFlash/DSpark 目前只能走 `--to hf`。**这条直接决定 B/C 两个模型能不能进端到端对比。**
2. **confidence head 该建模哪种验证协议** —— 先于本次改动就存在,与裁剪正交。当前 `Σ min(q,p)` 对应拒绝采样式 speculative decoding;若服务端用贪心或"与 target 一个采样比对",公式还要再对齐。仓库内部本来就有三套口径并存。
3. **NPU 上的布尔行索引** —— 见 §5。
4. **多卡 / 多机未实测** —— 见 §5。
5. **训练期解压开销没消掉** —— 只修了启动那一遍。实践上直接 `gunzip`,采集时别加 `--compress`。
6. **训练进度可观测性** —— epoch/ETA 上报还在 `SpecForge` 仓库的 `feat/epoch-progress-reporting` 分支上未提交(`specforge/training/progress.py`)。当前跑长任务只能靠 step 数推算进度。

**后续优化方向(未做)**:target 的全词表 log-normalizer 是每 token 一个标量,完全可以在采集阶段和 `target_last_hidden_states` 一起存下来(1 float vs 248320,带宽可忽略),那样接受率修正引入的额外全词表投影可以完全省掉。没做是因为要改 capture contract、normalizer、collator 和离线存储格式,并会让已采集的特征失效。

## 附:怎么用

**一行开关**(draft config **顶层**,不要放进 `dflash_config`):

```json
"vocab_size": 248320,
"draft_vocab_size": 64000
```

**先扫描再定 K**(不写文件):

```bash
python scripts/build_vocab_mapping.py \
    --data-path ./cache/dataset/train.jsonl \
    --tokenizer-path <target> --chat-template qwen3.5 --max-length 4096 \
    --draft-model-config configs/qwen3.6-27b-dspark.json \
    --draft-vocab-size 16000,32000,48000,64000
```

**过滤退化对话**(必须和训练用同一套参数):

```bash
python scripts/filter_trainable_conversations.py \
    --input-path ./cache/dataset/train.jsonl \
    --output-path ./cache/dataset/train_4096.jsonl \
    --tokenizer-path <target> --chat-template qwen3.5 --max-length 4096
```

**要盯的三个信号**:

| 信号 | 阶段 | 含义 |
|---|---|---|
| `top K token frequency ratio: XX%` | 建图 | 接受率天花板 |
| `draft_vocab_coverage` | 训练日志 | 按 token 计数的覆盖率,裁剪路径生效的标志 |
| `teacher_kept_mass` | 训练日志 | 按概率计的教师质量存活比例,界单步接受概率 |

**坑**:yaml 里设了 `model.vocab_mapping_path` 就会跳过自动建图;采集时加 `--compress` 会让训练期每个样本都付一次解压。
