## 1. 结论

这轮复核确认了两个会直接阻断主链路的问题，并已修复：

1. stock SGLang v0.5.14 的 Qwen3 没有
   `set_dspark_layers_to_capture`，离线 DSpark 会在构建 target model 时失败；
   现在会优先使用 DSpark hook，缺失时有告警地回退到 DFlash hook。
2. 新 SpecForge 会向 managed-local server 传
   `--spec-capture-method dspark`，旧 patch 只接受 `eagle3/dflash`；因此部署端
   必须同步升级 patch。Ascend 的 CPU segment mount 已合入主 v0.5.14 patch，

## 2. P0-1：离线 DSpark 抓特征断链

### 2.1 判断依据

完整代码路径是：

```text
scripts/prepare_hidden_states.py
  -> DSpark OfflineCaptureLayout.capture_method = "dspark"
  -> OfflineSGLangCaptureBackend.set_capture_layers()
  -> target model capture hook
```

合并后的 provider 把 offline/streaming 的 method 都改为 `dspark`。原
`set_capture_layers()` 将它硬映射为 `set_dspark_layers_to_capture`，`getattr`
失败就抛 `RuntimeError`。stock v0.5.14 Qwen3 只有 DFlash hook，因此用户指出的
Qwen3-8B / Qwen3.6-27B 离线链路确实会在第一次 forward 前断掉。

DSpark 和 DFlash 在该 backend 消费同一组 aux hidden states 和 last hidden
state，区别只是模型注册 hook 的名字，所以 fallback 不改变 feature schema。

### 2.2 修复

`specforge/offline_capture/sglang_backend/capture.py` 现在：

1. 优先调用模型原生 `set_dspark_layers_to_capture`；
2. 原生 hook 不存在或不可调用时，回退到
   `set_dflash_layers_to_capture` 并打 warning；
3. 两个 hook 都不存在才抛 `RuntimeError`。

`tests/test_offline_capture/test_sglang_capture_hooks.py` 分别覆盖 fallback、
原生 hook 优先和双 hook 缺失。3 项通过。

## 3. P0-2：capture server patch 必须同步升级

### 3.1 为什么旧 patch 不能继续用

新 launch plan 传 `--spec-capture-method dspark`，新 client 发送
`max_new_tokens=0`，即纯 prefill。`068009f` 的旧 patch：

- 参数说明和 model-runner 分支只识别 `eagle3/dflash`；
- sink 是逐请求同步 `put_from`；
- 对应的旧 client 使用 `max_new_tokens=1`。

当前 patch 接受 `dspark`，让 stock target 走 DFlash aux 管线，并实现批量异步
capture streaming。因此“只升级 SpecForge、不升级已部署 server”不是受支持
组合。

### 3.2 正确升级步骤

先停止 producer、consumer 和 capture server。以下命令必须在**实际安装
SGLang 的同一个 Python 环境**执行。`OLD_PATCH` 必须从旧提交取，不能拿当前新
patch 去 reverse 旧树。

```bash
REPO=/path/to/SpecForge-dspark-vocab
OLD_PATCH=/tmp/spec-capture-068009f.patch

git -C "$REPO" show \
  068009f:patches/sglang/v0.5.14/spec-capture.patch > "$OLD_PATCH"

SGL_PARENT=$(python -c \
  'import os, sglang; print(os.path.dirname(os.path.dirname(sglang.__file__)))')

# 先只检查；失败就不要继续，改为重装干净的 sglang==0.5.14。
patch --reverse --dry-run -p2 --batch -d "$SGL_PARENT" < "$OLD_PATCH"

# 用原 patch 精确卸载旧实现。
patch --reverse -p2 --batch -d "$SGL_PARENT" < "$OLD_PATCH"

# 手工 reverse 后删除旧 patch 记录，避免 apply 脚本再次 reverse。
rm -f "$SGL_PARENT/sglang/.spec_capture_patch.applied"

# 应用当前分支的新 patch；脚本内部使用 `python`，先确认它指向上述环境。
cd "$REPO"
python -c 'import sys, sglang; print(sys.executable, sglang.__version__)'
scripts/apply_sglang_spec_capture_patch.sh --target v0.5.14
```

如果第一条 reverse dry-run 失败，说明安装树不是精确的旧 patch 状态。不要用
`-f` 强行改；重装干净的 `sglang==0.5.14` 后直接运行 apply 脚本。

升级后检查：

```bash
python -m sglang.launch_server --help | \
  grep -E -- '--enable-spec-capture|--spec-capture-method'

python - <<'PY'
from pathlib import Path
import sglang

sink = Path(sglang.__file__).parent / "srt" / "spec_capture_sink.py"
text = sink.read_text()
assert '"dspark"' in text
assert "batch_put_from" in text
assert "allocate_and_mount_segment" in text
print(sink)
PY
```

最后用一个 prompt 做 online smoke，验收条件是请求只做 prefill、响应带
`meta_info.spec_capture`、Mooncake 中所有返回 ref 可读，然后再恢复生产流量。

### 3.3 兼容矩阵

| SpecForge/client | server patch | 结论 | 依据 |
| --- | --- | --- | --- |
| 旧 `068009f` | 旧 `068009f` patch | 旧的已知组合 | `dflash` + `max_new_tokens=1` + 同步 sink |
| 旧 `068009f` | 当前 patch | 代码协议可兼容，但不是本次发布验收组合 | 新 patch 仍接受 `dflash`，返回 schema 未删除；旧 client 仍会多做 1 token decode |
| 当前 `0812_upstream` | 旧 patch | **不兼容** | `dspark` 不被旧 model-runner 接受；旧 sink 也没有新版 zero-decode/异步路径 |
| 当前 `0812_upstream` | 当前 patch | 目标组合 | `dspark` 走 DFlash aux、`max_new_tokens=0`、异步 batch put |

离线 `prepare_hidden_states.py` 不使用 server patch；它依赖第 2 节的本地 hook
fallback。Kimi-K3 仍使用独立 `--target kimi-k3-9acd9cb` patch 和模型原生
DSpark hook。

## 4. P1-1：扫描历史 feature

### 4.1 风险成立

训练 normalizer 会先按 `data.max_length` 截断 `loss_mask`，再调用
`has_consecutive_supervised_tokens`。没有两个相邻监督 token 就抛
`ValueError`。旧 feature 没经过同一 predicate，且训练长度小于抓取长度时，
监督 token 可能恰好被截掉，所以可以在训练中途才失败。

### 4.2 扫描器

新增 `scripts/scan_offline_feature_eligibility.py`，遍历 `.ckpt/.ckpt.gz`，按目标
长度复现训练判定，并区分“原本就无效”和“由截断导致无效”：

```bash
/Users/wuyidong/.local/bin/python3.11 \
  scripts/scan_offline_feature_eligibility.py \
  --hidden-states-path /path/to/existing/features \
  --max-length 2048 \
  --invalid-paths-output /tmp/invalid-features-maxlen2048.txt \
  --json
```

退出码 0 表示全部兼容；存在任意无效样本时退出码 1。输出字段包括
`invalid_after_truncation`、`truncation_induced_invalid` 和
`invalid_at_full_length`。gzip、分类计数、路径输出及非零退出码均有单测。

仓库工作区里没有生产 `.ckpt/.ckpt.gz`，所以这里不能填写生产数据的命中数。
上线前必须在实际目录针对训练 YAML 的 `data.max_length` 跑一次。

### 4.3 命中后的方案

首选是按当前规则重抓/重建 feature。不要把上游 `raise` 直接改成默认 skip：
运行时 skip 会改变 dataset 长度、分布式 sampler 的分片和 step 顺序，并使同一
checkpoint 的 resume 数据序列变化，这会破坏上游“非法样本尽早硬失败”的
语义。

如果重抓成本不可接受，可以后续增加**显式 opt-in** 的过滤清单模式：在训练
启动前固定扫描结果、记录目录指纹和 `max_length`，所有 rank 读取同一份过滤后
manifest，并禁止跨 manifest resume。这种实现保留默认 raise；本次没有在训练
热路径加入静默 skip。

## 5. P1-2：`default_kv_lease_ttl`

当前 Mooncake [官方部署文档](https://github.com/kvcache-ai/Mooncake/blob/main/docs/source/deployment/mooncake-store-deployment-guide.md)
列出了 `--default_kv_lease_ttl`，但本机没有昇腾环境实际使用的
`mooncake_master`，因此无法确认 vendor build 是否包含它。
`examples/configs/qwen3.5-4b-dflash-disaggregated-npu.yaml` 已显式设置：

```yaml
deployment:
  disaggregated:
    managed_local:
      mooncake:
        default_kv_lease_ttl_ms: null
```

`null` 会让 launch plan 完全不生成该 CLI 参数。上机先执行：

```bash
if mooncake_master --help 2>&1 | grep -q -- '--default_kv_lease_ttl'; then
  echo 'supported: managed-local 可设置 default_kv_lease_ttl_ms: 500'
else
  echo 'unsupported: 保持 default_kv_lease_ttl_ms: null'
fi
```

500 ms 只缩短 key lease 回收等待，不改变 feature 数据格式。未完成上述探测前，
昇腾 recipe 保持 `null`。

## 6. P1-3：Ascend Mooncake segment

### 6.1 mount patch

原 `spec-capture-ascend-mount.patch` 没有 apply 入口，还会修改旧版 sink 的同一
hunk；在新版异步主 patch 后再叠加并不可靠。本次已把它删除，并将逻辑并入
`patches/sglang/v0.5.14/spec-capture.patch`：

- 同时检测 `ASCEND_RT_VISIBLE_DEVICES` 和 `ASCEND_VISIBLE_DEVICES`；
- Ascend 下 `store.setup(global=0, local=0)`，避免 `location:*`；
- 再调用 `allocate_and_mount_segment(configured_size, protocol, "cpu")`；
- mount API 缺失或返回非零都会硬失败，不会以零容量静默启动；
- CUDA/ROCm 继续使用原 `store.setup` 路径。

因此使用当前主 patch 时**不需要、也不应该**手工再打一份 Ascend overlay。
静态 patch 测试保护了两个环境变量、CPU mount 和零 wildcard buffer；目标机仍需
按第 3 节做真实 apply + server smoke。

### 6.2 `local_buffer_size=0` 是否与容量调优冲突

不冲突，但旧配置名容易误导：

- `local_buffer_size_bytes` 是 client staging buffer；Ascend 上因 wildcard
  location 不受支持而被强制为 0，现在非零配置会打印 warning；
- `global_segment_size_bytes` 是 capture server 存放 feature 的真实容量，主
  patch 会把它显式 mount 到 CPU，不会被清零丢失；
- `runtime.in_flight_high_watermark/low_watermark` 控制尚未消费的样本/引用数量，
  不由 local buffer 推导，原先按单样本体积调出的水位仍然有效。

昇腾 server 环境应把 `MOONCAKE_LOCAL_BUFFER_SIZE=0` 写清楚，容量继续按
`MOONCAKE_GLOBAL_SEGMENT_SIZE` 与 in-flight 水位计算。

## 7. P2 行为变化

### 7.1 最小 loss token 与数据基线

`dflash_min_loss_tokens()` 现在返回 2，DSpark provider 同时提供
`has_consecutive_supervised_tokens`。前者是粗粒度最小 token 门槛，后者保证
截断后的监督位置确实相邻。保留上游语义，不回退为 `2 * block_size`。

影响是同一原始语料的入选样本和 loss 分布可能变化；旧 loss/吞吐/收敛曲线不能
直接当新分支基线，必须用新规则重建数据基线。

### 7.2 mapping 与 resume

重新跑 prepare 可能产生不同的 t2d/d2t。模型的 state-dict pre-hook 会逐元素
比较当前 mapping 和 checkpoint mapping，不同就拒绝加载，避免 pruned lm_head
行含义静默变化；对应冲突 mapping 单测仍在。

历史文档中的 mapping 路径
`/dpc/hot/w00958190/dspark/configs/vocab_600k_64000/vocab_mapping.pt` 未挂载到
当前开发机，因此“旧 mapping 已归档”**尚未确认**。任何旧 checkpoint resume
前必须在存储侧完成：

```bash
MAPPING=/dpc/hot/w00958190/dspark/configs/vocab_600k_64000/vocab_mapping.pt
ARCHIVE=/path/to/checkpoint-archive/vocab_mapping.pt
test -r "$MAPPING"
test ! -e "$ARCHIVE"
install -m 0444 "$MAPPING" "$ARCHIVE"
sha256sum "$MAPPING" "$ARCHIVE"
```

将 SHA256、draft config、数据目录指纹和 checkpoint 一起归档。resume 必须让
`model.vocab_mapping_path` 指向该归档副本，不能指向重新 prepare 生成的新文件。

### 7.3 `--num-samples` 的 600k smoke 成本

默认行为保持上游语义：有 `loss_mask_filter` 时全量 tokenize/filter，再从合格
样本取 `--num-samples`。这保证 `num_samples=N` 真的是从整个确定性 shuffle 中
选出的前 N 个合格样本，但 600k smoke 会付出全量 tokenization 成本。

本次新增一个可向上游提交的 opt-in 优化：

```bash
... --num-samples 1000 --filter-candidate-samples 10000
```

它在正常确定性 shuffle 后、tokenize 前只取 10000 个候选，再过滤并要求至少有
1000 个合格样本；不足会硬失败，不会静默少抓。省掉的是剩余候选的 tokenize
和 filter；HF 原始数据构建、全量读取以及 shuffle index 构建仍可能覆盖 600k，
所以不能把它描述成完全按 1000 条读取。参数缺省时行为和上游完全一致。

### 7.4 draft config 解析失败的异常

组合可复现：设置 `model.vocab_mapping_path`，但 draft config 无法读取时，旧逻辑
把 `_prunes_vocabulary=False` 当成“全词表”，随后报“remove the path”，遮住原始
文件/解析异常。

现在 mapping-path 分支要求 `_prunes_vocabulary` 传播原异常；未设置 mapping 的
路径仍让后续 model-loading boundary 负责报错。回归测试用 `OSError("draft config
is unavailable")` 验证最终收到的仍是该异常。

### 7.5 radix cache 默认值

managed-local server 默认 `sglang_disable_radix_cache=True`，离线 prepare CLI
默认 False。两者生命周期不同：server 是长驻服务；离线 backend 每个 capture
batch 新建 `RadixCache`，并在 finally 中清空 request/KV pool，没有跨 batch prefix
复用。因此离线默认开启 radix 数据结构不产生跨 batch cache hit，对 600k 抓取
不应有实质吞吐收益，也不影响 feature 数值语义。

白盒复核还发现离线的 `ServerArgs.disable_radix_cache` 虽已由 CLI 设置，但
`CacheInitParams(disable=False)` 曾被写死，导致 `--sglang-disable-radix-cache` 没有
完整生效。本次已改为从 server args 透传，并增加构造 cache 的单测。SGLang
v0.5.14 的[官方 `RadixCache` 源码](https://github.com/sgl-project/sglang/blob/v0.5.14/python/sglang/srt/mem_cache/radix_cache.py)
在 `disable=True` 时会直接返回空 prefix match、跳过 insert，
所以这是开关语义修复，不改变默认 False 时的行为。

本次不擅自统一默认值。需要规避特定 target/backend 的 radix 兼容问题时，离线
显式加 `--sglang-disable-radix-cache`；managed-local 若是必须使用 unified radix
tree 的 hybrid target，则在 YAML 显式设 `model.sglang_disable_radix_cache: false`。
